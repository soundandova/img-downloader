# 一键看图下载（Edge 扩展）

一键扫描当前页面（含**分页**）的所有图片，按**真实尺寸**过滤后下载到以页面标题命名的文件夹，或打包为同名的 ZIP。

针对 `everia.club` 这类"一篇图集分多页、图片托管在另一个域"的站点设计，但**站点无关**——只要页面有分页链接就能跟进。

---

## 安装（Edge，开发者模式）

1. 打开 `edge://extensions/`
2. 左下角开启「**开发人员模式**」（不开启的话第 3 步的按钮不会出现）
3. 点「**加载解压缩的扩展**」，选择本目录（**这一层里能直接看到 `manifest.json`**，不要选到 `lib` 里面）
4. 图标默认被收进拼图菜单：点地址栏右侧 🧩 → 找到「一键看图下载」→ 点眼睛图标固定

改完代码需要在 `edge://extensions/` 点卡片上的刷新 ↻ 才生效。

---

## 用法

1. 在目标页面点扩展图标
2. 点 **扫描页面**：
   - 注入采集当前页（能读 `naturalWidth`，尺寸最准）
   - 顺着分页链接把**整篇文章每一页**都抓下来解析
   - 对每张图发 `Range: bytes=0-65535`，**只取 64KB 解析图片文件头**拿真实尺寸（不下载整图）
   - 自动填一个最小尺寸建议（可改）
3. 在网格里核对（尺寸/格式/大小/来源域名，可排序筛选）
4. 二选一：
   - **下载选中** → `下载\<页面标题>\001_原名_1200x1800.webp`
   - **打包 ZIP** → `下载\<页面标题>.zip`

### 开关

| 开关 | 作用 |
|---|---|
| **只算正文** | 只在正文容器（`.entry-content` / `article` / `main`…）里找图，排除侧栏「相关文章」缩略图 |
| **探测多页** | **默认开**。关闭则只扫当前页，一个分页请求都不发 |
| **上限 N 页** | 多页探测的页数上限（2–60）。命中上限时统计行会提示「还有未抓的分页」 |
| **绕防盗链** | 临时启用 DNR 会话规则（移除 `Referer`、伪装 `sec-fetch-*`）。仅当图床返回 403/HTML 时用 |
| **建同名文件夹** | 逐张下载时按页面标题建子目录 |

### 抓取节奏（折叠区）

| 参数 | 默认 | 范围 |
|---|---|---|
| 分页并发 | 4 | 1–8 |
| 页间隔 | **0ms** | 0–2000 |
| 尺寸探测并发 | 6 | 1–12 |

`页间隔` 默认 0：并发泳道本身已经限制了请求频率，再加固定间隔只会更慢（实测每页多等 100ms）。

## 「队列」是什么意思

状态栏里 `正在抓取分页… 已处理 N / M 页（队列待抓 K）` 说的是**分页的待处理清单**：

```
第 1 页抓完 → 发现"这文章还有第 2~7 页" → 放进队列
→ 泳道空出就立刻补位去抓 → 每个再把自己发现的页推进队列 → 队列空了就结束
```

站点无关：不需要预先知道总页数，页面给出什么分页链接就跟到什么。
三个数字互不重叠：`已处理 + 队列待抓 + 在飞 = M`。

> **修过的 bug**：早期版本并发抓取时没把这一批从队列移除，导致它们同时被算进"队列待抓"和"已处理"，
> 于是一篇 **6 页**的文章被显示成"文章共约 **11 页**"。现在有回归项守着：
> `已处理 + 队列 + 在飞 == 总数`、且**同一页不会被抓两次**。

## 性能：瓶颈在哪（实测）

### 瓶颈是「请求数 × 往返延迟」，不是网速

| 阶段 | 目标站点实测 | 决定因素 |
|---|---|---|
| 当前页注入采集 | **~15 ms** | 基本免费（DOM 已在内存里） |
| 分页抓取（7 页） | ~2 秒（好时）/ ~8 秒（站点慢时） | 每页一次请求 + 站点响应时间 |
| 尺寸探测（121 张） | ~1.8 秒 | **121 次独立小请求**（每次 64KB） |
| ZIP 打包（32.6MB） | **6 秒 / 0 失败** | 真正拼带宽，但带宽很宽裕 |

证据：探测 121 张图只传了 7.6MB，按带宽算不到 1 秒，实际耗时全花在 121 次往返上。
反过来，真正拼带宽的 ZIP 阶段（32.6MB）只要 6 秒 —— **带宽不是瓶颈**。

### 站点响应时间极不稳定（这是"卡在进度"的主因）

实测同一篇文章的不同分页，浏览器侧响应时间在 **434ms ~ 12.6 秒** 之间波动。

早期实现对此很脆弱：它按"一次取 N 页、等整批都回来再发下一批"来做，
**最慢的那一页会把整批空转拖住**。实测同一篇文章：

| 实现 | 总墙钟 | 进度回调次数 |
|---|---|---|
| 批次屏障（旧） | **7321 ms** | 3 次（一次跳 4 页） |
| 泳道补位（现在） | **2015 ms** | 6 次（逐页递增） |

改动：`crawlPages` 改成**泳道补位**——任一泳道空出就立刻取下一页，没有批次屏障；
同时把默认页间隔从 100ms 降到 0。**同一篇文章快 3.6 倍**。

### 慢页会直接告诉你

扫描结束后统计行会写：`有 N 页响应超 3 秒（最慢 X.Xs，站点侧）`。
想深挖可以用 `node tools\perf.js <URL>`，它会打印每页耗时与内部状态。

## 关于图片格式：原样保存，不做转换

**下载到的是服务器上的原始字节，没有任何解码 / 重编码。** 实测取证（`tools\format-audit.js`）：

```
本地文件 : 001_GRA10V097_1_1200x1800.webp  290332 字节  sha256=a48837bb8e44e081
服 务 器 : GRA10V097_1.webp                290332 字节  sha256=a48837bb8e44e081
→ 字节完全一致
```

目标是 **webp**，因为**站点本身存的就是 webp**（响应头 `Content-Type: image/webp`），不是扩展转换的。
在该站找过 jpg / png / 更大尺寸版本，**全部 404**，页面里 `srcset` 也是 0 处 —— 1200×1800 就是能拿到的最大版本。

**不建议转 jpg**，实测（`tools\format-quality.py`，PSNR/SSIM 逐像素对比）：

| 转换 | 文件大小 | 相对原图 | PSNR | 主观 |
|---|---|---|---|---|
| **原始 webp** | **290,332B** | 100% | — | 基准 |
| JPEG 质量 75 | 214,147B | 74% | 39.65 | 细看可见 |
| JPEG 质量 85 | 310,532B | **107%** | 41.78 | 极难分辨 |
| JPEG 质量 95 | 606,257B | 209% | 46.09 | 肉眼不可分辨 |
| PNG（无损） | 2,236,930B | 770% | ∞ | 完全无损 |

结论：**转 jpg 是纯亏** —— 想保画质文件反而更大，想变小就必须掉画质（两者不可兼得）；
而且输入已是有损 webp，任何再编码都是第二代损失。webp 在 Edge / Windows 10+ / 主流图片软件都已原生支持。

## 实现上踩过的坑（都已实测确认，别再踩）

1. **MV3 service worker 里没有 `URL.createObjectURL`**
   实测 `URL` 上只有 `length,name,prototype,canParse,parse`；也没有 `document` / `DOMParser`。
   → 每页 HTML 用正则解析（已用真实页面验证）；ZIP 的抓取/组装/落盘全部放在 popup 里做（省掉 `offscreen` 权限）。

2. **`chrome.runtime.sendMessage` 会把对象 JSON 序列化**
   JSZip 实例传过去后原型丢失，调用 `generateAsync` 报 `is not a function`。
   → 不要把带方法的对象跨上下文传递。

3. **`chrome.runtime.onMessage` 的广播在本机不可靠**
   同一上下文里**后装的监听器能收到 90+ 次，先装的收 0 次**。
   → 扫描/下载的进度改成"写 `storage.local` + popup 轮询"，不再依赖广播。

4. **`downloads.onChanged` 同样不可靠**
   3 张小图其实瞬间就写完了，但事件迟迟不来，导致一直等到 180 秒超时才返回。
   → `waitForDownloads` 改成轮询 `chrome.downloads.search`。

5. **`chrome.downloads.download()` 的 `filename` 不接受带目录的路径**
   传 `测试目录/文件名.png` 会被丢弃目录并把文件名替换成默认名（ZIP 会变成随机 UUID）。
   → `filename` 只传文件名，目录靠后台 `downloads.onDeterminingFilename` 的 `suggest()` 给。

6. **反斜杠在注入字符串里会被吃掉**（写测试工具时踩的）
   把正则 `/\/(\d+)\/?$/` 放进模板字面量后变成 `//(d+)/?$/`，注入代码直接语法错误。
   → 注入的代码里避免用含 `\/` `\d` 的正则，或在工具里做语法预检。

附带修掉一个真 bug：`while (size-- > s.length)` 是后缀自减，位宽被算成 `size-1`，
序号只补 1 个零（`01_` 而不是 `001_`）。单测当时没抓到，因为**测试桩把它写对了反而掩盖了源码的错**；
现在测试直接从源码抠 `pad`。

```
                     / 文件名强制 / 作业状态写回 / DNR 开关
  popup.html/css/js  界面 + ZIP 全流程（抓取 → JSZip 组装 → blob URL → downloads）
  lib/jszip.min.js   JSZip 3.10.1
  icons/             16 / 48 / 128
tools/
  test-parser.js       解析器单测（直接从 background.js 抠真实函数来测）
  e2e.js               Edge + CDP 真机端到端（支持真实站点与本地 fixture）
  fixture-site.js      本地分页测试站（8 页 x16 张、真实 PNG、可模拟慢页）——不依赖外网

  diag.js / probe-sw.js                聚焦诊断与 MV3 能力探测
```

## 验证方式

```powershell
# 启动本地 fixture 站点（稳定、不依赖外网）

node tools\test-parser.js                            # 解析器单测 39 项
node tools\e2e.js http://127.0.0.1:8099/article/1/   # fixture 端到端 39 项
node tools\e2e.js                                    # 真实站点端到端（受站点抖动影响）
node tools\e2e.js --full                             # 追加整篇 ZIP（真实站点约 35MB）
```

## 设计取舍

- **尺寸未知的图不丢**：只对"已知尺寸且小于阈值"的图做过滤，未知的放行并在网格标注「尺寸未知」。
- **不用 `webRequest`**：省掉常驻监听权限。代价是抓不到"从未进 DOM 的图"。
- **ZIP 在 popup 里做**：省掉 `offscreen` 权限。代价是**打包期间别关 popup**；关掉就改用「下载选中」。
- **`STORE` 不压缩**：图片本身已压缩，DEFLATE 纯烧 CPU。
- **DNR 规则只在任务期间存在**：`updateSessionRules` 加、`finally` 里删，不常驻。
- **下载结果以浏览器下载记录为准**：不猜，直接查 `chrome.downloads.search` 核实写入数量与体积。

## 已知限制

- 分页只跟进**同一路径族**的链接（`/post/2/`、`/post/3/`…），不会爬到站内其它文章；上限 60 页。
- 单次最多探测 800 张图的真实尺寸，超出部分按"尺寸未知"放行。
- 打包在 popup 里做，**关掉 popup 会中断**。
- 纯 CSS 背景图受限于正文容器内前 5000 个元素。
- `iframe` 内的图片不采集（未开 `all_frames`）。
- 下载进度的写回在某些情况下会失败（后台进程在长任务中被回收），此时界面会在约 12 秒后
  自动收尾，并**从浏览器下载记录核实真实结果**，不会永久卡住。
- 分页章节里偶尔会出现"页首重复上一页末图"或返回短页，这属于站点行为，扩展照实抓取。
